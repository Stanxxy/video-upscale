## 4. PASS rules — carry over UNCHANGED, explicit ruling on why

**Gate 1**: `hit_T − hit_S ≥ 4` on the core-30 (`fp_dup_rate_T ≤ fp_dup_rate_S + 5pp`). **Gate 2**: `net_delta ≥ 2` of 16. **Gate 5**: straddler-vs-core hit-rate gap `> 25pp` flips to NO-GO.

**None of these margins change for the re-run.** Each was derived from **sample size** (the smallest gap distinguishable from single-event noise at n=30/n=16/n=8 respectively) — a property of *how many windows/clips exist in the frozen subset*, not of which model is being scored or how well it is expected to perform. Loosening a margin now, after already having seen the flash-lite numbers and knowing a stronger model is coming, would be the exact post-hoc goalpost-moving this design was built to prevent — a NO-GO on a weak model followed by a conveniently softened bar for the "real" model is not a credible experimental record. If the qualified model produces a clean, large-margin result, it will clear the unchanged bar easily; if it's marginal, the same bar applies exactly as fairly as it did to flash-lite. **No noise-floor argument changes with model identity** — noise floor here is about event-count, not model capability.

### 6.2 Kimi K3 (via OpenRouter) — call shape is a two-branch decision tree, resolved by one probe

Founder directs Kimi K3 runs via OpenRouter (OpenAI-compatible endpoint, likely model id `moonshotai/kimi-k3` — confirm exact slug against OpenRouter's model list at implementation time, never guess a slug and silently 404-fallback to something else). **One engineer probe resolves the whole call shape — do it before writing any Kimi driver code:**

  - **If YES** — build a native-video Kimi call path mirroring Gemini's shape exactly: same `fps=10`, same window, no frame-subsampling at all. This is the **preferred outcome** — it removes the temporal-resolution confound entirely for Kimi (see §6.3) and gives the cleanest possible model-only comparison against `gemini-3.5-flash`'s own Arm T.
  - **If NO (frames-only — the founder's own stated probable default)** — Kimi reuses the **exact same frame-extraction and subsampling** Opus already uses (`claude_frames.sample_frames`/`subsample_evenly`, ≤20 evenly-spaced JPEG frames per window), rebuilt against OpenRouter's OpenAI-compatible chat-completions schema (images as `{"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}}` content blocks, not Anthropic's native `{"type":"image","source":{...}}` shape — the two providers' multimodal message schemas are NOT interchangeable, this must be a real second content-builder, not a copy-paste that happens to work). **This is what makes Kimi and Opus DIRECTLY, frame-for-frame comparable to each other** (same input, two different frontier models) even though neither is then directly comparable to Gemini's native-fps=10 arms without the §6.3 caveat.

**One-time refactor recommendation** (not required, but the cheap right call given both Kimi-frames and Opus now share one input-preparation path): factor `subsample_evenly`/frame-sampling out of `claude_frames.py` into a small provider-agnostic helper, with two thin per-provider message-builders (Anthropic-native, OpenAI/OpenRouter-compatible) on top. Flagged as a recommendation because it reduces future duplication risk (two independently-drifting frame-extraction implementations), not because either lane is blocked without it.

### 6.3 Frame-lane comparability ruling — a SEPARATE experiment, not a confound-free A/B against Gemini

**For our actual window (`[t_s−5s, t_s+4s]`, 9 seconds — the design's own §A.4 cut, not a generic "10–30s" window):** ≤20 evenly-spaced frames over 9s ≈ **2.2 effective fps**, versus Gemini's native `fps=10` — a **~4.5x reduction in temporal sampling density**, before any question of model capability. **Ruling, explicit: any comparison between a frames-lane model (Opus always; Kimi if the §6.2 probe comes back frames-only) and `gemini-3.5-flash`'s native-video Arm T answers a DIFFERENT, blended question — "are frontier reasoning models better highlight analysts even at ~4.5x lower temporal resolution" — NOT the clean, single-variable "is this model better at the same architecture" question Gate 1 was built to answer.** Two variables move at once (model identity AND temporal sampling density), and there is no way to hold temporal density fixed for Opus specifically (Claude Vision has no native-video path at all, this is a hard platform limit, not a configuration choice). Report every frames-lane-vs-Gemini comparison with this caveat attached, every time, never as a Gate-1-equivalent verdict — this is the same discipline `VERDICTS.md` already applied to the Files-API-vs-YouTube-URI ingestion-path confound in Gate 3, extended to a second, independent nuisance variable here.

**If Kimi's §6.2 probe comes back YES (native video)**: Kimi-vs-Gemini becomes a clean single-variable model comparison (no temporal confound), while Opus-vs-Gemini remains the confounded frames-vs-native comparison above — the two frontier models would then sit at DIFFERENT levels of comparability to the Gemini baseline, and the report must say so explicitly rather than presenting "the frontier lane" as one uniform comparison.

### 6.4 What it measures, n, and budget (all three lanes now confirmed-run, not conditional)

**Sub-lane A (always runs) — same-architecture, cross-model comparison.** Run Arm T's three axis calls (position/technique/validator, maximum thinking per §6.2's per-model mapping) for BOTH Opus and Kimi against the **same reduced sub-sample of Gate 1's frozen core-30** (never a new draw — first-by-window_id deterministic slice, extended per the cost rule below). Compare each model's hit rate against `gemini-3.5-flash`'s own Arm T hit rate on the identical windows (§6.3 caveat attached to every such comparison) AND against each other (Kimi-frames vs. Opus-frames — or Kimi-native vs. Opus-frames if §6.2 resolves to native video for Kimi — a same-input-modality-or-better, directly interpretable comparison either way).

**Sub-lane B (secondary, confound-flagged) — Arm-S-equivalent.** No frame-sampled Arm-S path exists for either model today (§6.1) — building one is out of scope here. Instead, reuse the ALREADY-CAPTURED `gemini-3.5-flash` Arm-S hit rate on the same windows (free) as an informational secondary figure: "best-available two-call setup (Opus/Kimi reasoning) vs. best-available single-call setup (Gemini)" — practically useful, explicitly model-AND-architecture-confounded, never reported as a clean verdict.

**Provider-route sanity check for Opus (mandatory before treating OpenRouter as Opus's default route).** The founder wants OpenRouter usable as the cost-efficient route for Opus itself, not just for Kimi — but direct-Anthropic and OpenRouter-proxied Opus are **not assumed scientifically equivalent** here, for concrete, non-hypothetical reasons: (a) OpenRouter's OpenAI-compatible schema does not guarantee a 1:1 pass-through of Anthropic-specific parameters like the `{"thinking":{"type":"adaptive"}}` shape — a proxy can silently downgrade to its own lowest-common-denominator reasoning control, which is exactly the kind of silent behavior change this project's "no silent fallback" discipline exists to catch; (b) default sampling/timeout/system-prompt handling can differ between a direct SDK call and a compatibility-layer call even for the identical nominal model. **Run 2 calls — same window, same prompt/schema, `thinking="high"` — one via direct Anthropic SDK (`claude_frames.py`'s existing path), one via OpenRouter targeting Opus — before using OpenRouter as Opus's default route.** Check: (1) does the response's usage block show real thinking-token consumption on BOTH routes (confirms the reasoning parameter was actually honored, not silently dropped, on the OpenRouter path); (2) do the two routes land on the same enum choice on an unambiguous test clip (structural agreement, not byte-identical text — sampling variance is expected and fine). If both checks pass, OpenRouter is the default route for all subsequent Opus calls (cheaper, per the founder's preference) and `"provider_route"` is recorded in every call's settings tuple regardless (auditable either way, per the CEO's explicit ask). If either check fails, use direct Anthropic exclusively for Opus, and record that decision with the failing evidence — never silently fall back without saying why.

**n and cost — per-model pilot, then scale.** Frame/image-token pricing and (for Kimi) unconfirmed reasoning-token consumption are NOT covered by the Gemini ledger data (§3) — run a **3-call pilot per model** (one position/technique/validator triple, on one frozen window) before committing to a full n, for THREE things at once: (1) real cost/call, (2) confirmation the reasoning/thinking parameter is actually honored (§6.2/provider-route check), (3) a basic schema/JSON-parse sanity check. Then scale: start at **n=12** (deterministic first-12-by-window_id slice of the core-30, no new draw), extend up to **n=30 (the full core-30 ceiling — never the 8 gate5-straddlers, not needed for this architecture question)** per model, independently, as far as projected spend allows. Budget split: Gemini re-run ≈$6 (confirmed, §5) leaves **~$94** for Opus + Kimi combined — allocate **up to $40 each with ~$14 contingency** as a starting soft split, but let real, pilot-measured cost-per-call drive the actual split (if one model is meaningfully cheaper, give it the larger n rather than holding a rigid 50/50 — more data from the cheaper model is a better use of the same dollar than an artificially equal split). Cap combined Opus+Kimi spend at **≤$85** of the $100 budget, preserving ≥$9 contingency on top of the Gemini re-run's own ≈$6.

## 8. Predictions (falsifiability) — on the record, before the data

**Does two-call vs. single-call flip at the qualified model?** My flash-lite confound analysis (`VERDICTS.md` §1) found the losses were NOT structural (zero validator ditches, an active 30% disagree rate) but calibration-driven (scattered technique-axis misclassification, `back_take` wrong 7/7 times with no consistent alternate label, `guard_pass→transition` under-crediting). A materially more capable, max-thinking model plausibly helps MORE with a decomposed, narrower-per-call judgment task than with one overloaded multi-field call — narrower questions benefit more from deeper reasoning per question. **Prediction: `hit_T − hit_S` improves from −1 (flash-lite) into the 0-to-+3 range at `gemini-3.5-flash`/max-thinking — a real, visible improvement in the two-call design's relative standing — but I do NOT confidently predict it clears the required +4 margin on this first qualified-model attempt.** This is a genuine, falsifiable bet, not a hedge calibrated to always be right either way.

**Does the arm_lock↔leg_lock taxonomy confusion survive better reasoning?** The flash-lite finding was that this specific error is **conceptual/taxonomy-boundary** (identical wrong answer — `submission_leg_lock` for `submission_arm_lock` gold — at BOTH resolutions, meaning more pixels didn't help, so it isn't primarily a visibility problem). I predict this pattern is **partially, not fully, reasoning-limited**: a stronger model with deeper "thinking" about biomechanical cues (which joint, which limb is trapped) should reduce the RATE of this specific error, but a genuine subset of these clips are true visual-ambiguity cases (fast scrambles, occluded grips) where no amount of reasoning substitutes for a clean view — reasoning helps you use what you can see better, it does not let you see through an occlusion. **Concrete, falsifiable prediction: Gate 2's `accuracy_low`/`accuracy_high` rise together from 50%/50% to somewhere in the 55–70% range at the qualified model, but I predict at least 2 of the 8 `submission_arm_lock` clips still misclassify as `submission_leg_lock` even at max thinking** (i.e., the specific confusion pattern reduces but does not vanish). **I further predict Gate 2's core HIGH-vs-LOW finding (no accuracy gain from resolution) is MORE LIKELY THAN NOT to persist** — since the identified mechanism is conceptual/reasoning-level, not visibility-level, "more thinking at the same resolution" should matter more than "more pixels at the same thinking level," and I expect Gate 2 to remain NO-GO on the resolution question specifically even if both arms' absolute accuracy improves. If the data instead shows a resolution-dependent split emerging at the qualified model that wasn't visible at flash-lite, that would falsify this prediction and would itself be a genuinely interesting finding — the qualified model "seeing more" in a way flash-lite structurally couldn't.

**Do the frontier-lane (Opus/Kimi) arms beat `gemini-3.5-flash` on Arm T, and does that mean anything for the architecture question?** Two predictions, kept deliberately separate because §6.3 says they answer different questions. **(1) On raw Arm-T hit rate**, I predict Opus (and Kimi, if it lands in the frames branch) **underperforms `gemini-3.5-flash`'s own Arm T on this specific corpus, despite being the more "frontier" model overall** — not because Opus/Kimi reason worse, but because ~2.2 effective fps over a fast, often-occluded 9s BJJ exchange is a real information loss that "more thinking" cannot recover (the same "reasoning can't see through an occlusion" logic as the arm_lock/leg_lock prediction above, now applied to temporal sampling instead of resolution). **Falsifiable bar: I predict Opus's Arm-T hit rate on the shared n-window sub-sample lands BELOW `gemini-3.5-flash`'s, by a visible (not razor-thin) margin** — if Opus instead matches or beats Gemini despite the 4.5x lower temporal density, that would be a genuinely notable finding (reasoning quality dominating temporal resolution on this task) and would directly undercut this prediction. **(2) If Kimi's §6.2 probe resolves to native video** (the scientifically cleaner case), I predict it fares meaningfully better than the frames-bound Opus run and is the more informative of the two cross-model comparisons — a real model-only signal, not confounded by sampling density. **(3) On what this means for the architecture question**: even a frontier-model win on Arm T would NOT, by itself, flip Gate 1's own verdict — Gate 1 is a same-model, `gemini-3.5-flash`-only, single-vs-two-call comparison (§4's unchanged margins), and the frontier lane cannot substitute for Sub-lane B's missing Arm-S equivalent (§6.4). The most this lane can honestly deliver is: "if you're willing to pay frontier-model prices and accept ~4.5x lower temporal sampling, here is how much of a reasoning-quality ceiling still exists above what Gemini finds" — a real, useful data point for a LATER product decision, not a substitute for Gate 1's own qualified-model verdict.

### 9.3 Reliability — explicit fixes, one stated halt threshold, no more inference

**Kimi `w8` and Opus `w6` JSON-parse failures — root-cause BEFORE the batch, not blindly patched.** These are two DIFFERENT-shaped failures and must not be assumed to share one fix:
- **Mandatory first step: read the actual captured `raw_response_text` for both** (`frontier_kimi_predictions.json`'s `w8` entry; `frontier_opus_predictions.json`'s `w6` entry — both already on disk, zero new calls needed to diagnose) before writing any parser change.
- **Opus `w6`** (`"Extra data: line 6 column 1"`) has the textbook signature of a complete, valid JSON object followed by trailing prose the model appended after it — `finish_reason="max_tokens"` didn't fire because the response wasn't truncated, it just kept talking after answering. **If the raw text confirms this shape**: switch parsing from a bare `json.loads(text)` (which requires the entire string to be valid JSON with nothing after it) to `json.JSONDecoder().raw_decode(text.lstrip())` (extracts the first complete JSON object, ignores everything after it) — **and log any non-empty discarded trailing text at WARNING level, every time**, so a systematic "model keeps talking after the JSON" pattern stays visible rather than silently normalized away. This is fail-LOUD-via-log, not silent.
- **Kimi `w8`** (`"Expecting value: line 157 column 1"`) is a different-looking signature — line 157 is far past where a ~50-260-token JSON answer should end, suggesting either a much-longer-than-normal response or a different failure mode entirely (not necessarily "valid JSON + trailing prose"). **Do not assume the Opus fix (`raw_decode`) applies here without first confirming what the actual raw text contains.** If it turns out to be the same trailing-content shape, the same fix applies; if it's something else (a genuinely malformed/incomplete body), the correct policy is to **keep failing loud** (recorded `call_failed`, as it already correctly did) rather than broaden the parser to paper over a different, unexamined bug.
